# Threat model and evidence

Scope: an untrusted requester or approver using the application's methods, including concurrent workers. The trusted operator owns the Python process, test enrollment, SQLite files, HMAC key and Floci bootstrap. This single-host pilot cannot defend against that operator. Synthetic authentication is not proof that two real people participated.

Results below refer to automated tests in this project. **Application** means enforcement in Python/SQLite. **Floci** means an actual emulator response. **Design** means production controls are still required; it does not imply effective AWS enforcement.

| Threat | Required control and enforcement point | Test / observed result | Residual risk / production requirement |
|---|---|---|---|
| Requester self-approval | Application compares authenticated canonical person with stored requester | `test_self_approval_including_dual_role`: both requester-only and dual-role cases pass | Trusted IdP must map every role/session of a human to the same subject |
| Two approvals from one person | Application unique `(request, person)` decisions; aliases canonicalized | `test_one_approval_and_alias_cannot_make_two`: pass | Registry operator can fabricate a second person; use directory-governed independent subjects |
| Forged identity or approved flag | Bearer authentication against trusted random-secret registry; no client identity input | `test_forged_identity_is_rejected`, `test_unauthorized_approver`: pass | Test tokens are not federated MFA identities; theft permits that synthetic principal's actions |
| One approval treated as a quorum | Application rechecks exactly two eligible non-requesters during claim | Approval tests and actual demo deny execution after one vote | Compromised executor code can skip checks unless protected independently |
| Approval replay | Durable signed terminal state and consumed execution/resource claim | `test_execution_and_receipt_without_credentials`, actual Floci replay test: pass | Whole database rollback by operator is outside local protection |

| Approval/runbook modification | No application edit API; design: restrict SSM document writes, versions and automation start | Local runbook guard/structure tests; offline requester/approver UpdateDocument denies pass | No effective SSM/AWS test. Document updater or alternate runbook/step execution can bypass naive orchestration |
| Executor IAM policy or code modification | Design: separate deployment administrators, protect IAM writes/PassRole and executor configuration | Offline `iam:PutRolePolicy` denial examples pass; requester/approver cannot claim in app | No real IAM/deployment permission validation; policy administrators remain privileged |

## Recovery rules

Do not change FAILED/COMPLETED/EXECUTING back to APPROVED. A definite failure before API submission can be corrected only by a new request with two new decisions. Unknown outcomes are quarantined, including when the target still appears present. Inspect the durable claim/receipt and independently verify the actual resource before deciding on a separately authorized recovery action.

For this disposable local environment, `reset-local.sh` destroys all fixtures and starts a new test trust domain. It is not a production recovery procedure. In production, restoring authorization state from a backup must not restore consumed capabilities: reconcile the external execution ledger and actual resources first.

Resource-marker mutation is intentionally exercised using the trusted test operator, not granted as a requester permission. The trusted deletion path never removes or fabricates a missing marker to make a request executable.
